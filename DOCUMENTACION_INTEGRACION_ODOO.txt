1. RESUMEN EJECUTIVO
--------------------------------------------------------------------------------
Se completó con éxito la integración total entre la aplicación móvil "ATRIO"
y el backend ERP Odoo 19 a través de su API REST/JSON. El sistema cuenta con:
- Almacenamiento seguro nativo (Android Keystore / iOS Keychain).
- Autenticación mediante tokens JWT (Access Token corto + Refresh Token rotativo).
- Interceptor automático para renovar la sesión en segundo plano ante errores 401.
- Resiliencia y fallback elegante en la interfaz ante reglas de negocio como
  el estado '403 membership_pending' (miembros pendientes de aprobación).
- Soporte para refresco manual (Pull-to-Refresh) en todas las pantallas integradas.
2. ARQUITECTURA DE INTEGRACIÓN
--------------------------------------------------------------------------------
A) Cliente HTTP Centralizado:
   - Archivo: lib/atrio_api.dart
   - Implementa llamadas seguras tipadas a los endpoints de Odoo.
   - Maneja automáticamente las cabeceras:
     * Content-Type: application/json
     * Accept: application/json
     * Authorization: Bearer <token> (excepto en /auth/login y /auth/refresh)
     * X-Odoo-Database: opcional según configuración multi-tenant.
   - Mutex anti-colisión: Usa un Completer thread-safe para que múltiples peticiones
     concurrentes que reciban 401 esperen a una sola llamada de /auth/refresh.
   - Carga perezosa auto-recuperable (_ensureStorageLoaded): Carga los tokens a memoria
     desde el disco seguro antes de cualquier llamada HTTP, resistente a Hot Restart.
B) Servicio de Persistencia Cifrada:
   - Archivo: lib/servicios/token_storage_service.dart
   - Utiliza la librería 'flutter_secure_storage' versión ^10.3.4.
   - Opciones nativas Android: aOptions: AndroidOptions(resetOnError: true) para
     evitar bloqueos por llaves huérfanas en el Keystore.
   - Opciones nativas iOS: KeychainAccessibility.first_unlock.
C) Gestión de Estado (Provider):
   - Archivo: lib/providers/user_provider.dart
   - Maneja el UserModel actual, el estado de carga y las notificaciones a la UI.
   - Auto-restaura la sesión al instanciarse la app y coordina el flujo de logout.

5. DICCIONARIO DE CÓDIGOS DE ERROR DE ODOO 19
--------------------------------------------------------------------------------
Código HTTP | Código Odoo              | Significado y Acción en la App
--------------------------------------------------------------------------------
400         | missing_fields, etc.     | Datos incompletos o inválidos en formulario.
401         | unauthorized, etc.       | Token ausente o vencido. La app lo renueva
            |                          | automáticamente con el refresh token.
403         | membership_pending       | El usuario inició sesión pero su membresía en
            |                          | la iglesia está pendiente de ser aprobada
            |                          | por el administrador/pastor en Odoo.
403         | subscription_required    | La iglesia requiere plan o suscripción activa.
404         | not_found, no_member     | El recurso no existe o no pertenece a la iglesia.
409         | event_full, event_past   | El evento ya no tiene cupos o ya finalizó.
500         | server_error             | Error interno del servidor Odoo.
6. GESTIÓN DE USUARIOS EN EL BACKEND DE ODOO
--------------------------------------------------------------------------------
Si en la app observas el mensaje:
"AtrioApiException(403, membership_pending): El acceso está pendiente de aprobación"
Esto indica que la conexión técnica es perfecta. Para que ese usuario pueda
consumir datos en vivo sin restricción:
1. Ingresa a la interfaz web de Odoo: https://atrioapp.odoo19rd.com
2. Accede al módulo de ATRIO / Miembros / Iglesias.
3. Localiza el perfil del usuario correspondiente (ej. juan@gmail.com).
4. Cambia el estado de su membresía de "Pendiente" a "Aprobado" o "Activo".
5. Al volver a la aplicación móvil y deslizar hacia abajo (pull-to-refresh),
   la API entregará inmediatamente los registros activos de la base de datos.
